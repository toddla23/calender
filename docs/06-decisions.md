# 06. 결정 기록

이미 내린 결정은 이유와 함께 남긴다. 뒤집으려면 사용자와 합의 후 새 항목으로 기록하고 이전 항목에 `→ D-0xx로 대체`를 적는다.

## 결정

### D-001. 개인용, 달력 하나 (2026-11-14 사용자 결정) → D-015로 대체
- 사용자 구분·달력 여러 개는 만들지 않는다. 나중에 여러 사람으로 넓힐 가능성만 열어 둔다.

### D-002. 인증은 Google 로그인 + `ALLOWED_EMAILS` 허용 목록 (2026-11-14 사용자 결정) → 허용 목록 부분은 D-017로 대체 (`*`면 누구나)
- 처음 스펙의 관리자 비밀번호 방식(12자, argon2)을 대신한다.
- 로그인 시도 제한(IP별 5회 → 15분)과 기기 토큰 정책(90일 미사용 만료, 폐기)은 그대로 둔다.
- 허용 목록이 비어 있으면 서버가 시작되지 않는다. 공개 서비스에서 "아무나 로그인"을 실수로 열지 않기 위해서다.

### D-003. 데스크톱 로그인은 시스템 브라우저 + 루프백 + PKCE
- 앱이 시스템 브라우저로 서버 로그인 페이지를 열고, 서버가 `127.0.0.1` 루프백으로 PKCE에 묶인 일회용 코드를 돌려준다.
- 이유: Google 쪽에 데스크톱용 클라이언트를 따로 만들 필요가 없고, 코드를 가로채도 앱 말고는 토큰으로 바꿀 수 없다.

### D-004. 서버는 파이에서 Tailscale Funnel로 공개하고, `127.0.0.1`에만 연다
- 서버는 `network_mode: host`로 `127.0.0.1:3000`에만 연다. `HOST=0.0.0.0`이나 금지 포트(8080, 3306, 5432, 22, 111, 631)를 넣으면 시작을 거부한다.
- 이유: 공개 경로를 Funnel 하나로 묶는다. 파이의 다른 서비스 포트와 겹치지 않게 한다.
- 결과: 클라이언트 IP는 소켓이 127.0.0.1일 때만 `X-Forwarded-For`의 맨 오른쪽 값을 믿는다.

### D-005. 서버는 Node.js + Fastify, esbuild 단일 파일 번들
- 메모리가 적게 들고 ARM64에서 네이티브 모듈 없이 돈다. 의존성까지 한 파일로 묶어 `node_modules` 없이 배포한다.

### D-006. 프론트엔드는 프레임워크 없는 바닐라 TS, 모든 플랫폼이 같은 코드
- 화면이 달력 하나라 프레임워크 이점이 작다. 달을 바꿀 때만 42칸을 만들고 이후에는 바뀐 칸만 다시 그린다.
- 웹·PWA·Tauri가 `web/`을 함께 쓰고, 데스크톱 전용 코드는 별도 청크로 뺀다.

### D-007. 데스크톱은 Tauri v2 (2026-11-14, 이전 Electron 구현을 대체)
- 시스템 WebView2를 써서 설치 파일이 작다(1.19MB). 바탕화면 부착·DPAPI 같은 Win32 기능을 Rust에서 바로 부른다.

### D-008. Android 앱은 TWA
- 네이티브 앱 대신 Chrome으로 웹앱을 주소창 없이 띄운다.
- 이유: 화면·기능이 웹앱과 같고, 서버를 업데이트하면 앱도 바로 바뀐다.
- 대가: Android 7.0 이상 + Chrome 필요. 서버가 `/.well-known/assetlinks.json`으로 서명 지문을 알려 줘야 주소창이 사라진다.
- 패키지 이름 `io.github.toddla23.batangcalendar`는 스토어에 한 번 올리면 바꿀 수 없다.

### D-009. 동시 수정은 덮어쓰지 않고 합친다
- `baseVersion`이 다르면 `서버 내용 + "--- 다른 기기에서 수정 ---" + 내 내용`으로 합치고 충돌 표시를 켠다. 합치기 전 두 버전은 이력에 남긴다.
- 이유: 메모는 짧은 글이라 사람이 보고 정리하는 편이 낫다. 마지막에 쓴 쪽이 이기면 한쪽 수정이 조용히 사라진다.
- 색은 예외로 마지막에 쓴 쪽이 이긴다. 색만 바꾼 op는 내용 충돌을 만들지 않는다.

### D-010. 이력은 날짜 칸당 100개 (2026-11-14 사용자 결정)
- `HISTORY_KEEP`으로 바꿀 수 있다. 부하가 크면 50개 이하로 줄여도 된다.

### D-011. JSON 가져오기는 파일에 있는 날짜만 덮어쓴다 (2026-11-14 사용자 결정)
- 전체 교체 모드는 만들지 않는다. 덮어쓴 칸은 이력에 남아 되돌릴 수 있다.

### D-012. 실시간은 WebSocket만, 폴링하지 않는다
- 놓친 변경은 재연결 때 `since` 조회와 이벤트 번호 빈 곳 감지로 채운다.
- 이유: 바탕화면 상주 앱의 유휴 CPU·네트워크를 0에 가깝게 둔다.

### D-013. 데스크톱 앱은 GPU 가속을 끈다 (`--disable-gpu`)
- 메모리가 107MB에서 67MB로 줄었다(GPU 프로세스 51MB → 7.5MB).
- 그림이 단순해서 소프트웨어 렌더링으로 충분하고, 투명 창도 정상으로 보인다.

### D-014. 모든 쓰기를 `sync_lock` 행 하나로 직렬화한다 → D-016으로 대체
- 이유: `seq` 순서와 커밋 순서가 같아야 `since` 조회에서 빠지는 변경이 없다. 사용자가 한 명이라 직렬화 비용이 문제되지 않는다.

### D-015. 사용자마다 자기 달력 하나 (2026-11-23 사용자 결정)
- Google 계정마다 달력이 따로 있다. 처음 로그인하면 빈 달력이 생긴다. 달력 공유·한 사람의 여러 달력은 만들지 않는다.
- 메모·이력·변경 번호·처리한 opId·기기 토큰은 모두 사용자에 속하고, 모든 API·WebSocket 이벤트는 자기 것만 다룬다.
- 기존 달력(002 마이그레이션 전 데이터)은 `ADMIN_EMAILS` 첫 번째 이메일(주인)의 것이 된다. 기존 토큰과 클라이언트 캐시의 `since`는 그대로 유효하다.
- 한 기기에서 계정이 바뀌면 이전 계정의 캐시·미전송 큐를 버린다. 다른 사람 달력에 섞이는 것보다 낫다고 봤다. 클라이언트는 `X-Deskcal-User`로 캐시 주인을 보내고, 서버는 토큰의 계정과 다르면 409로 거부한다.
- 이유: 여러 사람에게 열려면 남의 메모를 읽거나 덮어쓸 수 없어야 한다.

### D-016. 쓰기는 사용자별로 직렬화하고 `seq`도 사용자별로 센다
- 쓰기 트랜잭션은 자기 `users` 행을 `FOR UPDATE`로 잠그고 `users.last_seq + 1`을 변경 번호로 쓴다. `sync_lock` 표는 지웠다.
- 이유: 번호를 전체에서 하나로 세면 남의 수정 때마다 클라이언트가 "빈 번호"를 보고 다시 받아 온다(D-012). 다른 사용자끼리는 기다리지 않는다.
- `changes`에는 날짜별 마지막 변경 번호만 남긴다(`since` 조회에 그것만 필요). 표가 끝없이 커지지 않는다.

### D-017. `ALLOWED_EMAILS=*`면 누구나 가입 (2026-11-23 사용자 결정)
- 허용 목록 방식도 그대로 쓸 수 있다. `*`일 때만 Google 계정이 있는 누구나 가입한다.
- `*`이면 `ADMIN_EMAILS`와 `CONTACT_EMAIL`이 없으면 서버가 시작하지 않는다. "허용 목록 전체가 관리자" 규칙이 "모두가 관리자"가 되는 것을 막고, 개인정보처리방침에 문의처를 적기 위해서다.
- 관리자가 아닌 사용자에게만 제한을 둔다: 가입 인원 `MAX_USERS`(기본 50), 저장 용량 `USER_QUOTA_MB`(기본 10MB, 메모·이력 각각), op 속도 `OPS_PER_MINUTE`(기본 600).
- 허용 목록에서 빠진 이메일은 이미 받은 토큰도 401이 된다.

### D-018. 저장 용량은 "내용 바이트 + 행마다 100"으로 센다
- 메모가 한도를 넘으면 메모를 키우는 저장만 거부하고, 줄이거나 지우는 저장은 받는다. 그래야 가득 찬 사용자가 정리할 수 있다.
- 이력이 한도를 넘으면 그 사용자의 가장 오래된 이력부터 지운다. 이력 때문에 저장이 막히지 않게 하기 위해서다.
- 행마다 100바이트를 더하는 것은 빈 메모를 아주 많이 만들어 DB를 키우는 것도 막기 위해서다.
- 사용량은 `users.note_bytes`·`history_bytes`에 쓰기 트랜잭션 안에서 갱신한다. 매번 합계를 다시 세지 않는다.

### D-019. 임시공휴일은 모든 사용자 공통, 관리자만 고친다
- 공휴일은 사람마다 다르지 않다. JSON 가져오기로도 관리자만 넣을 수 있다.

### D-020. 계정 삭제는 즉시, 되돌릴 수 없다
- 설정 → 계정 삭제. 실수를 막으려고 본인 이메일을 다시 입력받는다. 메모·이력·기기 토큰을 바로 지우고, 백업에는 `BACKUP_KEEP`일 동안 남는다(개인정보처리방침에 적음).

## 열린 질문 (해당 기능 착수 전에 사용자에게 묻는다)

### O-01. 플레이스토어에 올릴지 (F15 전)
- 올리면 Play 앱 서명 지문을 `ANDROID_CERT_SHA256`에 넣어야 한다(07-release 3.4).

### O-02. 2028년 이후 공휴일
- 지금 데이터는 법 규정으로 계산한 값이다. 매년 월력요항이 나오면 대조해 고친다.

### O-03. 윈도우 설치 파일 코드 서명
- 지금은 서명이 없어서 처음 실행할 때 SmartScreen 경고가 뜬다.

### O-04. 누구나 가입의 기본 한도값 (F17 승인 전) → 2026-11-23 사용자 확인: 기본값 그대로
- 지금 기본값: 가입 50명, 메모·이력 각각 10MB, 1분 600 op. 파이 저장 공간과 쓰려는 인원에 맞는지 확인한다.

### O-05. Google 로그인 앱 게시 (누구나 가입을 켜기 전) → 2026-11-23 해결: Search Console HTML 파일로 소유권 확인, 브랜딩 인증·게시, 프로덕션 전환
- OAuth 동의 화면이 "테스트" 상태면 등록한 테스트 사용자만 로그인된다. "프로덕션"으로 게시해야 한다(08-hosting 6절).
- 2026-11-23 첫 인증 제출 결과: 홈페이지 소유권 미확인, 개인정보처리방침 내용 부족(그때 `/privacy`가 아직 배포 전이라 로그인 화면이 보였음), 홈페이지가 로그인 화면. → `/about`·`/terms`, 보강한 `/privacy`, Search Console HTML 파일 확인을 만들었다. 배포 후 다시 제출한다.
- `ts.net` 하위 도메인을 URL 접두어 속성으로 확인한 것을 Google 이 받아 주는지는 아직 모른다. 안 되면 직접 소유한 도메인이 필요하다.

### O-06. 개인정보처리방침·이용약관 문구 (F17 승인 전) → 2026-11-23 사용자 확인: 그대로
- 초안은 Claude 가 썼다. 만 14세 미만 이용 불가, 서버 위치 대한민국, 책임 제한 문구는 운영자가 확인한다.
